# T5 보안 검토 — 계산 결과 조작 방지 (2026-11-02)

- 대상: `T5-DB-초안/040_trip_rpc.sql` 의 "클라이언트가 계산 결과(p_calcs)를 보내고 RPC 가 저장" 구조
- 결론: **현재 초안 그대로는 운영에 쓸 수 없다.** 조작된 클라이언트가 입력과 다른 인정시간을 저장·승인시킬 수 있다. 저장 전 서버가 **DB 에 있는 입력 원본으로 다시 계산**하는 구조로 바꿔야 하며, 이 프로젝트 안에서는 **기존 Vercel Function(`api/`) 패턴**으로 새 서비스·비용 없이 가능하다.
- 실행한 것 없음. DB·외부 리소스 변경 없음. 아래 코드는 초안이며 적용은 사용자 승인 후.

## 1. 위협 시나리오별 판정

"현재 초안" = 040 그대로. "권장안" = 2절 구조.

| # | 시나리오 | 현재 초안 | 권장안 |
|---|---|---|---|
| 1 | 클라이언트가 출장 인정시간을 임의로 바꿔 보냄 (예: 4h → 40h) | **취약.** `_trip_store_calc` 는 형식·규칙 버전·소속만 검사하고 `result` 수치를 그대로 저장 | 차단: 클라이언트는 계산 결과를 보내지 않는다. 서버가 DB 입력으로 계산 |
| 2 | 입력 원본과 계산 결과 불일치 (입력은 08~17, 결과는 06~22 기준) | **취약.** `entry_snapshot` 은 서버 입력을 복사하지만 `result` 와 대조하지 않음. 관리자 화면 재계산(완화 2)은 T7 과제라 아직 없음 | 차단: 결과는 항상 서버 입력에서 나옴. 추가로 `review` 가 `entry_snapshot = 현재 entry` 를 다시 검사 |
| 3 | 규칙 버전·지역 표준시간 조작 (`ruleVersion` 바꿔치기, `engineInput.regions` 에 없는 코드) | **부분 취약.** 버전은 "존재" 만 검사(`UNKNOWN_RULE_VERSION`), 시행일 미검사. `engineInput.regions` 와 `trip_regions` 대조 없음. 엔진의 `REGIONS` 는 코드 상수라 클라이언트 번들을 고치면 다른 값으로 계산 가능 | 차단: 서버 엔진 상수 사용. 저장 시 `rule_version = 활성 버전`, `engine_input.regions ⊆ trip_regions(유효 기간)` 를 DB 제약·RPC 에서 검사 |
| 4 | 승인 이후 입력 변경 | **방어됨.** 승인 뒤 `trip_update_draft` 는 `NOT_EDITABLE`, 관리자 수정도 `submitted` 만 허용. 승인은 `trip_reviews.calc_ids` 에 고정 | 동일. 추가로 `trip_claim_days` 에 "approved 상태 claim 의 근무일 UPDATE 금지" 트리거 권장(2-4) |
| 5 | 직원이 관리자 권한 가장 (role 을 admin 으로 보냄) | **방어됨.** RPC 는 역할 인자를 받지 않고 `auth.uid()` → `employees.role` 로 판정 | 동일. 메모리 게이트의 `ROLE_MISMATCH` 와 같은 효과 |
| 6 | 기능 OFF 상태에서 직접 RPC 호출 | **방어됨.** 모든 공개 RPC 첫 줄 `trip_require_feature()`. 단, **조회(SELECT)** 는 RLS 로만 막히고 플래그를 보지 않음 → OFF 여도 본인 행 조회 가능 | 조회도 막으려면 RLS 정책에 `trip_feature_enabled('employee_form')` 조건 추가 (2-5). 메모리 게이트는 이미 조회까지 거부 |
| 7 | 같은 신청 중복 제출·동시 수정 | **방어됨.** `expected_version` → `VERSION_CONFLICT`, 제출 후 `NOT_EDITABLE`, UNIQUE(직원, 근무일). 단 두 RPC 가 동시에 같은 행을 읽는 경쟁은 `select … for update` 가 있어야 확실 | `trip_claims` 를 `for update` 로 잠근 뒤 버전 비교 (2-6). 메모리 서비스는 단일 스레드라 해당 없음 |
| 8 | 승인 기록과 계산 결과 불일치 (승인 뒤 계산 행 삭제·변경, 다른 claim 의 calc id 끼워 넣기) | **부분 방어.** `trip_day_calcs` 는 UPDATE/DELETE 금지. `STALE_CALC` 가 "최신 calc id 집합 = expected" 를 검사하므로 다른 claim 의 id 는 걸림 | 동일 + `trip_reviews.calc_ids` 각 원소가 같은 claim 의 calc 인지 CHECK 트리거 (2-7) |

요약: **1·2·3 이 핵심 구멍**이고 모두 "클라이언트 계산 결과를 믿는다"는 한 가지 원인에서 나온다. 6·7·8 은 보강 수준.

## 2. 권장 구조 — 서버가 DB 입력으로 다시 계산

### 2-1. 흐름

```
직원 화면 ──(입력 원본만)──▶ RPC trip_create_claim / trip_update_draft   [계산 결과 받지 않음]
                                   │  (입력 저장, status=draft, version+1)
                                   ▼
직원 화면 ──(claim_id, JWT)──▶ Vercel Function  api/trip-compute.ts
                                   │  1. JWT 검증 (anon client, 기존 api/admin-user.ts 와 같은 방식)
                                   │  2. service_role 로 trip_claims·trip_claim_days·holidays·trip_regions 읽기
                                   │  3. computeClaimDays()  ← src/features/trip/data/compute.ts (이미 분리됨)
                                   │  4. service_role 전용 RPC _trip_store_calc_server(claim_id, calcs) 호출
                                   ▼                                   (engine_source='server', computed_by=호출자)
trip_day_calcs (불변)
                                   ▲
관리자 화면 ──(approve, expected_calc_ids)──▶ RPC trip_review
                                   │  최신 calc 가 engine_source='server' 이고
                                   │  calc.day_revision = day.revision 이고 entry_snapshot = day.entry 일 때만 승인
```

- `trip_submit` 도 "모든 근무일의 최신 calc 가 `server` 이고 revision 일치" 를 요구한다. 아니면 `CALC_STALE_OR_UNTRUSTED` 로 거부 → 화면은 자동으로 compute 를 다시 부른다.
- 미리보기는 지금처럼 브라우저에서 같은 엔진으로 계산한다 (표시 전용). 저장되는 값은 서버 계산뿐이다.
- `computeClaimDays` 는 저장소에 기대지 않는 순수 함수라 Vercel Function 에서 그대로 import 된다 (`src/features/trip/data/compute.ts`, 테스트 10건).

B 를 권장한다. C 는 B 가 안 될 때의 대안이고, A 의 수치 검증은 B 에도 **방어선으로 함께** 넣는다(2-3).

### 2-3. B 에서도 `_trip_store_calc` 에 남길 검증 (방어선)

서버 계산이라도 버그·회귀를 잡기 위해 저장 직전에 확인한다. 위반 시 `CALC_INVARIANT` 로 거부.

1. `rule_version` = `trip_rule_versions` 에서 근무일에 유효한 활성 버전 (시행일 미정 동안은 `is_active=true` 1건)
2. `engine_input.regions` 의 모든 코드가 `trip_regions` 에 있고 근무일에 유효
3. 수치: 전부 `>= 0`, `trip_hours <= 2 × 최대 편도(4h) = 8`, `overtime_hours + trip_hours <= 24`, `holiday_* <= 24`
4. `entry_snapshot` = 그 근무일의 현재 `entry` (jsonb 동등), `day_revision` = 현재 revision
5. `engine_source = 'server'` 이고 호출자가 service_role (`current_setting('request.jwt.claims')` 의 role 확인) — 클라이언트 세션에서 이 함수 EXECUTE 권한 회수
6. `computed_by` 는 함수가 받은 JWT 의 사용자 (감사용)

### 2-4 ~ 2-7. 보강 항목

- **2-4** `trip_claim_days` BEFORE UPDATE 트리거: claim.status ∈ (approved, rejected, cancelled) 이면 거부 (관리자 수정 RPC 도 submitted 만 허용하지만 테이블 수준에서 한 번 더)
- **2-5** RLS SELECT 정책에 `public.trip_feature_enabled('employee_form')`(직원) / `('admin_review')`(관리자) 조건 추가 → OFF 면 조회도 0행
- **2-6** `trip_update_draft`/`trip_submit`/`trip_review` 에서 `select … from trip_claims where id = p_claim_id for update` 후 버전 비교
- **2-7** `trip_reviews` INSERT 트리거: `calc_ids` 각 원소가 `trip_day_calcs.claim_id = new.claim_id` 인지 확인
- **2-8** 같은 날 기존 야근(`overtime_requests`): compute 함수가 `otherRequestLookup` 으로 같은 직원·같은 날짜·status not in (cancelled, rejected) 를 조회해 `OTHER_REQUEST_SAME_DAY` 확인 항목을 붙인다 (코드 쪽은 이미 구현, 서버 조회만 연결)
- **2-9** 공휴일: `holidays` 에서 `is_verified` 행만 모아 `HolidayCalendar{verified: true, source: 'holidays 테이블 (검증 N건)'}` 로 넘기고, 검증 행이 0이면 `NO_CALENDAR` → 모든 날 `HOLIDAY_SOURCE_UNVERIFIED`

### 2-10. `api/trip-compute.ts` 초안 (적용 전 — 여기에만 둠, `api/` 에 넣지 않음)

```ts
// api/trip-compute.ts — 초안. 기존 api/admin-user.ts 의 JWT 검증·CORS 패턴을 그대로 따른다.
import type { VercelRequest, VercelResponse } from '@vercel/node'
import { createClient } from '@supabase/supabase-js'
import { computeClaimDays } from '../src/features/trip/data/compute'
import { NO_CALENDAR, type HolidayCalendar, type TripDayRecord } from '../src/features/trip/data'
import { RULE_VERSION } from '../src/features/trip/engine'

export default async function handler(req: VercelRequest, res: VercelResponse) {
  if (req.method !== 'POST') return res.status(405).end()
  const jwt = req.headers.authorization?.replace(/^Bearer /, '')
  if (!jwt) return res.status(401).json({ code: 'UNKNOWN_USER' })
  const anon = createClient(process.env.VITE_SUPABASE_URL!, process.env.VITE_SUPABASE_ANON_KEY!, { global: { headers: { Authorization: `Bearer ${jwt}` } } })
  const { data: me } = await anon.auth.getUser()
  if (!me?.user) return res.status(401).json({ code: 'UNKNOWN_USER' })

  const svc = createClient(process.env.VITE_SUPABASE_URL!, process.env.SUPABASE_SERVICE_ROLE_KEY!)
  const { claimId } = req.body as { claimId: string }
  // 1) 기능 스위치 (서버 값)
  const { data: enabled } = await svc.rpc('trip_feature_enabled', { p_key: 'employee_form' })
  if (!enabled) return res.status(403).json({ code: 'FEATURE_DISABLED' })
  // 2) 본인 건 또는 admin — employees.role 로 판정 (요청 본문의 역할은 쓰지 않음)
  // 3) claim·days·holidays·regions 읽기 → HolidayCalendar 구성 (검증 행 0건이면 NO_CALENDAR)
  // 4) computeClaimDays({ header, employeeId, days, calendar, findActiveDay, otherRequestLookup })
  // 5) svc.rpc('_trip_store_calc_server', { p_claim_id, p_calcs, p_computed_by: me.user.id, p_rule_version: RULE_VERSION })
  // 6) 응답: 저장된 calc id 목록 (화면은 이 id 로 제출·검토)
  void NO_CALENDAR; void (null as unknown as HolidayCalendar); void (null as unknown as TripDayRecord)
  return res.status(501).json({ code: 'NOT_IMPLEMENTED', note: '초안' })
}
```

`SUPABASE_SERVICE_ROLE_KEY` 는 Vercel 환경변수에만 있고 브라우저 번들에는 들어가지 않는다 (`VITE_` 접두사 없음). 이 함수 자체도 호출자의 JWT 를 먼저 검증하므로 임의 호출로 남의 신청을 계산할 수 없다 (본인 건 또는 admin 만).

## 3. 040 초안에 대한 구체적 수정 지시 (적용 시)

1. `trip_create_claim`, `trip_update_draft` 에서 `p_calcs` 인자 **제거**. `_trip_apply_calcs` 호출 제거.
2. `_trip_store_calc` → `_trip_store_calc_server(p_claim_id, p_calcs, p_computed_by, p_rule_version)` 로 바꾸고 2-3 검증 추가. `revoke execute … from anon, authenticated` 유지, service_role 만 실행.
3. `trip_submit`: 모든 근무일의 최신 calc 가 `engine_source='server'` 이고 `day_revision` 일치 → 아니면 `CALC_STALE_OR_UNTRUSTED`.
4. `trip_review`(approve): 같은 조건 + `entry_snapshot = day.entry`.
5. `trip_day_calcs.engine_source` CHECK 를 `('server', 'edge')` 로 바꾸고 기본값 제거 (`'client'` 값 자체를 불허).
6. 2-4 ~ 2-7 트리거·정책 추가. 2-8 조회를 compute 함수에 연결.
7. `900_rollback.sql` 에 새 함수·트리거 역순 삭제 추가.

이 수정은 사용자 승인 후 에이전트에게 한 번에 맡길 수 있는 범위다.
