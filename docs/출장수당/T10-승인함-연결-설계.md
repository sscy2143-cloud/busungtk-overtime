# T10 — 기존 승인함과 출장 승인 연결 구조 설계 (2026-11-06)

구현 전 설계다. 기존 승인 화면(`AdminApprovalsPage`)은 바꾸지 않았고, 일반 근태 UX/UI 감사와 IA 개편이 따로 진행 중이라 그 결과가 나오기 전에는 코드를 만들지 않는다.

## 현재 구조
- 야근·휴가 승인: `/admin/approvals` (`AdminApprovalsPage`), 화면이 테이블을 직접 update 한다.
- 출장 검토·승인: `/admin/trip` (`AdminTripPage` → `AdminTripReview`), 상태 변경은 RPC 로만 한다(`trip_review`).
- 두 화면은 완전히 분리돼 있고 서로 호출하지 않는다. 출장 승인은 대표(admin)만, 야근 승인도 대표만이다.

## 연결 방식 비교
| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 링크·배지 | 승인 화면 상단에 "출장 검토 대기 n건 → 이동" 배지만 추가 | 기존 화면 변경 최소, 위험 낮음 | 한 곳에서 처리하는 것은 아님 |
| B. 통합 대기함 | 새 읽기 전용 목록이 야근·휴가·출장의 대기 건을 한 줄씩 보여 주고 각 승인 화면으로 이동 | 한 곳에서 "무엇이 밀려 있나" 확인, 기존 승인 로직 불변 | 새 화면 필요, 대기 건수 조회 설계 필요 |
| C. 기존 화면에 출장 탭 삽입 | `AdminApprovalsPage` 안에서 출장도 승인 | 진짜 한 화면 | 기존 승인 화면 수정 — 보안 패치·UX 감사와 충돌 위험, 승인 로직 재사용 불가(출장은 RPC·계산 고정) |

**권장: A → B 순서.** C 는 기존 승인 로직과 출장의 "계산 결과 고정·확인 항목·버전 충돌" 구조가 달라 합치면 위험하다.

## 안 B 구현 시 구조(제안)
- 데이터: 출장 대기 건수는 `reviewQueue('submitted')` 로 이미 얻는다. 야근·휴가 대기 건수는 기존 화면이 쓰는 조회를 읽기 전용으로 재사용(새 DB 변경 없음).
- 위치: `src/pages/` 의 얇은 글루 화면 하나. 출장 기능 폴더(`features/trip`)는 야근 코드를 import 하지 않는다(독립성 테스트 유지).
- 권한: admin 만. 일반 직원·인사담당(manager)에게는 메뉴가 없다. 서버(RPC·RLS)가 최종 판정한다.
- 스위치: 출장 부분은 `TRIP_FEATURE.adminReview` 가 꺼져 있으면 표시하지 않는다.
- 표시 항목: 종류, 신청자 표시, 날짜, 제출 시각, 상태. 금액·시급·급여는 표시하지 않는다.
- 새 DB 객체 없음 → 운영 SQL 추가 변경 없음.

## 테스트 계획
- 스위치 OFF 면 출장 줄이 나오지 않는다. admin 이 아니면 거부된다.
- 대기 건이 없을 때 빈 상태, 건수가 많을 때 정렬(제출 순).
- 기존 승인 화면 코드·테스트는 변경하지 않는다(git diff 로 확인).
- 독립성: `features/trip` 안에서 야근 모듈 import 금지.

## 결정이 필요한 것
1. 안 A 만 먼저 할지, B 까지 할지.
2. UX 감사·IA 개편과의 순서(감사 결과를 기다릴지).
3. 야근 대기 건수를 어떤 조회로 읽을지(기존 `overtime_requests` 읽기 권한은 admin 에게 이미 있음).
