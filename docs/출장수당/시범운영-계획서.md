# 출장수당 시범 운영 준비 (2026-11-06)

기능은 아직 OFF 다. 이 문서는 시범 운영을 켜기 전에 정해야 할 것과 켠 뒤의 절차를 정리한 준비 자료다. 직원 공지나 활성화는 하지 않았다.
규정 항목은 임의로 확정하지 않았고, 결정 칸은 비워 둔다.

## 1. 시범 운영 대상 선정 기준 (제안, 결정 필요)
- 인원: 대표가 지정하는 소수(3~5명 권장). 출장 빈도가 높고 수기 계산을 같이 해 줄 수 있는 직원.
- 유형 분산: 당일 / 숙박 / 사무실 근무 후 출발 / 토요일 / 제외 지역(수도권) 이 최소 1건씩 나오도록 한다. 일요일·공휴일, 제주, 다음 날 09시를 넘긴 작업은 규정 미정이 걸려 있으므로 첫 달에는 "관리자 확인" 건으로만 받는다.
- 기간: 급여 마감 1주기(약 1개월) 이상. 같은 기간의 수기 계산이 있어야 비교가 된다.
- 제외: 퇴사 예정자, 규정 해석 분쟁 중인 직원.
- 동행 출장은 직원마다 따로 신청한다(동행자에게는 초안만 간다).

## 2. 담당자용 수기 대조 절차
1. 시범 직원은 출장을 마친 뒤 신청한다(근무 후 신청 원칙). 승인 전에는 수기 계산을 보지 않는다.
2. 담당자(인사)는 신청서의 입력값(지역, 현장 시각, 점심 사용 여부)만 보고 최종본 규정(HANDOFF 1-2절)대로 **수기로 계산**해 표에 적는다. 시스템 계산 결과는 보지 않는다.
3. 대표가 승인한 뒤 관리자 화면 `/admin/trip` 의 "시범 비교" 탭에서 시스템 결과 CSV 를 내려받는다.
4. 담당자의 수기표를 같은 열 형식으로 올린다: `ref, date, trip, nightTravel, overtime, nightOvertime, holidayWithin8, holidayOver8` (시간 단위, 비면 0).
5. 화면의 대조 결과에서 일치·차이·한쪽에만 있음을 확인한다.
- 이 비교는 급여에 아무것도 쓰지 않는다. 화면과 코드 모두 급여 반영과 연결되지 않는다.

## 3. 일치·불일치 처리 기준 (제안)
| 상황 | 처리 |
|---|---|
| 일치 | 기록. 단, "회사 결정 전 값 포함" 표시가 있으면 일치로 세지 않고 결정 대기 목록에 둔다 |
| 차이 있음 | 같은 입력으로 양쪽 계산을 다시 해 본다 → ① 수기 오류면 수기표 정정 ② 시스템 오류가 의심되면 입력값과 최종본 해당 절을 붙여 개발 담당에게 전달(계산 엔진의 19개 사례 테스트에 사례로 추가) ③ 규정 해석 차이면 아래 결정표로 올린다 |
| 시스템에만 있음 | 수기표 누락. 담당자가 보완 |
| 수기표에만 있음 | 직원이 신청하지 않았거나 미승인. 신청 여부 확인 |
| 허용 오차 | 0시간(시 단위 계산이므로 정확히 같아야 일치). 시범 중 오차를 두려면 별도 결정 |
- 시스템 값을 수기값에 맞춰 임의로 고치지 않는다. 입력이 같다면 어느 쪽이 맞는지는 규정으로 판단한다.

## 4. 관리자 승인 검수 체크리스트
- [ ] 신청자가 본인이다(동행자는 각자 신청했다). 본인 건을 본인이 승인하지 않는다.
- [ ] 지역 선택이 실제 출장지와 맞다. 여러 지역이면 첫 지역과 마지막 지역이 맞다.
- [ ] 현장 시작·종료 시각이 업무 기록과 맞고, 점심 사용 여부가 맞다.
- [ ] 같은 날 야근 신청과 겹치지 않는다(겹치면 확인 항목이 뜬다).
- [ ] 관리자 확인 항목(노랑)을 모두 읽고 처리했다. 처리하지 않은 항목이 있으면 승인되지 않는다.
- [ ] "제안값 · 회사 확정 전" 표시 항목을 확인했다(급여에 들어가지 않음을 안다).
- [ ] 공휴일·일요일이면 휴일 근로 처리와 담당자 확인을 거쳤다.
- [ ] 승인 후 수정이 필요하면 사유를 적고 수정했다(수정 이력이 남는다).

## 5. 규정 결정표 (E3~E7, N1, N2) — 결정 칸은 비워 둠
시스템은 아래 항목에서 "제안값"을 만들고 관리자 확인을 요구한다. 결정되면 계산 규칙의 상태만 바꾼다(테스트 사례도 같이 갱신).
| 항목 | 쟁점 | 권장안(HANDOFF 3절) | 결정 전 시스템 동작 | 결정자 | 결정 결과 |
|---|---|---|---|---|---|
| E3 | 5-3(사무실 근무 후 출발 등)에서 남는 시간이 출장보다 많거나 점심을 못 써 모자랄 때 | 남으면 출장 → 연장 순으로 빼고, 모자라면 연장에 더함(E2·E8 과 함께 적용) | 제안값 + 관리자 확인 | 대표·노무 | |
| E4 | 5-3 에서 표준 이동을 어느 시각에 놓을지 | 작업 시작 − T 와 종료 + T. 회사 지시 대기가 있으면 앞에. 겹치면 사무실 종료 직후 + 관리자 확인 | 제안값 + 관리자 확인 | 대표 | |
| E5 | 숙박 중간일(이동 없는 날) 근무 유형 | 유형 ⑦ 신설, T = 0 으로 4절 적용 | 제안값 + 관리자 확인 | 대표 | |
| E6 | 제주: 실제 시각이 필요한데 2절은 실제 시각을 안 씀 | 제주만 실제 시각 예외(증빙 필수), 인정 = max(8, 실근무). 전제 3가지(출발 기준, 공항 대기, 전부 연장 여부) 확정 필요 | 항상 관리자 확인 | 대표·노무 | |
| E7 | 다음 날 09시를 넘겨 이어진 작업 | 09시에서 나눔, 휴게를 반드시 뺌, 주 한도 초과 시 특별연장 여부 확인 | 항상 관리자 확인 | 대표·노무 | |
| N1 | 야간 연장 시간의 배분(연장 중 몇 시간이 야간인지) | 규정에 없어 제안값. 실제 작업 시각 기준 제안 | 야간 연장만 제안값 | 대표·노무 | |
| N2 | 점심시간이 이동 중에 걸릴 때 | 빼지 않고 제안값 표시 | 제안값 표시 | 대표 | |
- 첫 시범 달에는 위 항목이 걸리는 건을 "관리자 확인" 으로만 받고, 결정이 나기 전에는 급여에 쓰지 않는다.

## 6. C-0 노무 확인 사항 (급여 적용 전 필수)
- 표준 편도 이동시간(지역별 1~4시간)을 근로시간으로 간주해 출장수당·연장수당 산정에 쓰는 것에 대해 근로기준법 제58조 서면합의 등 근거가 있는가.
- 표준 이동시간을 실제 이동과 다르게 정액으로 인정하는 방식이 불리한 변경이 되지 않는가(기존 야근 수당 기준과의 관계).
- 실제 야간 근로(22~06시)에 가산이 필요한 구간(E2)의 처리.
- 주 단위 한도(출장 + 연장 8/12시간 경고, 40시간 초과분 판단, E9)와 특별연장(제53조 제4항) 적용.
- 휴일 근로(일요일·공휴일)의 8시간 이내/초과 처리.
- 기록 보관 3년(표준시간과 실제 시각 병행 보관)의 충족 여부.
- 결과는 서면으로 남기고 결정표 5절에 반영한다.

## 7. 공휴일 데이터 출처 검증
- 시스템은 공휴일 달력을 코드에 고정하지 않는다. 달력이 "검증됨"이 아니면 모든 날에 확인 항목이 붙어 승인이 막힌다.
- 점검 절차: ① 시범 기간(월) 공휴일·대체공휴일 목록을 공식 출처(관보·인사혁신처 공고)와 대조해 `holidays` 표 입력안을 만든다 ② 두 사람이 교차 확인 ③ 출처 이름·확인 일자를 함께 기록 ④ 검증됨으로 표시.
- 임시공휴일 등 사후 변경이 생기면 해당 월을 다시 검증한다.

## 8. 실제 직원 사용 전 점검표
- [ ] 출장수당 SQL(005·010·020·030·040)이 운영에 적용됐고 사후 점검 SQL 결과가 정상이다.
- [ ] 코드가 Production 에 배포됐고(기능 OFF) 기존 야근·승인·직원관리 화면이 정상이다.
- [ ] 직원관리에서 시범 대상과 팀장 직급(조회 권한 후보)이 정리됐다.
- [ ] 공휴일 달력이 검증됨 상태다.
- [ ] 결정표 5절의 해당 항목이 결정됐거나, "제안값 + 관리자 확인"으로 운영하기로 서면 확인했다.
- [ ] C-0 노무 확인 결과가 있다(급여 반영 전 필수. 시범 비교 단계에서는 급여에 쓰지 않으므로 시범 개시 자체의 조건은 아님 — 대표 판단).
- [ ] 수기 계산 담당자가 지정됐고 비교 절차를 연습했다.
- [ ] 직원 공지문(`직원공지문_초안.md`)과 도입 당일 체크리스트(`도입당일_체크리스트.md`)가 확정됐다.
- [ ] 장애 시 기능을 다시 끄는 방법(스위치 OFF)과 연락 체계가 정해졌다.

## 9. 기능 ON 을 위한 별도 승인 조건
스위치를 켜는 것은 별도 승인이다. 아래가 모두 충족돼야 한다.
1. 위 8절 점검표 완료.
2. 시범 대상 직원 명단과 기간에 대한 대표의 서면 승인.
3. 켜는 대상은 직원 입력(`employee_form`)과 관리자 검토(`admin_review`)뿐이다. **급여 반영(`payroll_apply`)은 DB 제약과 코드로 켤 수 없고, 시범 결과와 C-0 확인 뒤 별도 변경이 필요하다.**
4. 켠 직후 점검: 대상 직원만 메뉴가 보이는지, 일반 직원에게는 안 보이는지, 신규 RPC 의 익명 접근이 막혀 있는지.
5. 문제가 생기면 즉시 스위치를 끈다(데이터는 보존).
