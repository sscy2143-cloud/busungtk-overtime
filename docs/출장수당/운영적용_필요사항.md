## 2. 운영 적용 시 바뀌는 것 / 바뀌지 않는 것

- 바뀌는 것: 신규 테이블 10개 + 함수·트리거·정책 (전부 `trip_` 접두사 또는 `holidays`). Vercel 함수 1개 추가.
- 바뀌지 않는 것: 기존 테이블·RLS·RPC·화면. `employees` 는 FK 참조만. 급여대장·`payslips` 는 건드리지 않음 (`payroll_apply` CHECK 로 true 저장 불가).
- 되돌리기 — 세 가지를 구분한다 (11-03 검토):
  1. **적용 트랜잭션 ROLLBACK**: 010→040 을 `begin; … commit;` 한 묶음으로 실행하다 오류가 나면 아무것도 남지 않는다(PGlite 에서 040 문법 오류가 났을 때 실제로 그랬다). 자료 손실 없음.
  2. **기능 끄기(운영 중 표준 되돌리기)**: `trip_set_feature('employee_form', false, '사유')`·`('admin_review', false, …)`. 표·자료·함수는 그대로, 화면·RPC·REST 조회가 전부 막힌다. 신청 자료가 생긴 뒤에는 이것이 유일하게 안전한 되돌리기다.
  3. **900_rollback.sql(객체 제거)**: trip_* 표 12개·함수·정책·뷰를 지운다 → **신청·계산·검토 기록이 함께 사라진다**(3년 보관 대상). 11-03 부터 `trip_claims` 에 행이 있으면 `ROLLBACK_BLOCKED_DATA_EXISTS` 로 멈추고, 내보내기 뒤 `set_config('trip.confirm_drop','yes',false)` 를 한 세션에서만 진행된다. 기존 표·정책·함수는 건드리지 않으므로 근태·급여 자료는 어느 경우에도 영향 없다.
  Vercel 함수는 파일 삭제 후 재배포.

## 4. 남은 기술 위험 (적용 후에도)

- SQL 은 PGlite(PostgreSQL 18)에서는 검증됐지만 **Supabase 운영 인스턴스(PostgreSQL 15/17, PostgREST, auth 스키마)에서는 아직 실행되지 않았다** → 대조 체크리스트 C-1~C-11 뒤 트랜잭션 단위 적용.
- `service_role` 판정(`current_setting('request.jwt.claims')`)이 Supabase 의 키 체계 변경과 함께 달라질 수 있다 → C-11.
- Vercel 함수 장애 시 제출·승인 불가 (잘못 저장되는 쪽으로 실패하지 않음).
- 엔진 버그는 서버·클라이언트가 같은 방향으로 틀린다 → 시범 운영 수기 병행.
- 계산 뒤 외부 조건(공휴일 검증·같은 날 야근)이 바뀐 경우 기존 계산은 "현재"로 남는다 → 5단계의 "검토 화면 열 때 계산 1회".
